Internal explainer · not the product

Watch an engineer decide if remote memory is worth it.

RmemFab is a deterministic simulator for memory placement. This page walks the full lifecycle — the question, the scenario, the run, the argument, the evidence — so you can explain it, recruit for it, and design a dashboard around it.

Recruiting artifact · redesign the UI from these wireframes
What it is
A discrete-event engine that turns a scenario into memory events, then metrics.
What it is not
A GPU emulator or a benchmark. It models memory movement, not kernels.
The decision it serves
Is remote capacity cheaper than local capacity at your latency target?
Build window
10 days · Muse AI Hackathon · Indie track
Stack
Python core · React dashboard · Meta open weights via Baseten
Core guarantee
Same scenario + seed + version = same result.
The mental model

Three objects, one loop.

Everything in the product is one of these. If a feature does not make the scenario more honest, the engine more trustworthy, or the verdict easier to argue, it is not in scope.

01 / SCENARIO

The system you have

Nodes, local DRAM, remote pools, fabric links, page size, workload, policy, faults, seed. Everything is a parameter. Nothing important hides in code.

→events
02 / ENGINE

The system you simulate

A priority-queue event loop resolves every page access against the hierarchy. Misses become transfers, migrations, prefetches — each with a cost.

→metrics
03 / VERDICT

The decision you defend

Latency percentiles, hit ratios, fabric saturation, cost. Every number traces back to an event and a parameter, not to a model's opinion.

Not a cycle-accurate hardware emulator
Not a replacement for a real CXL cluster
Not an LLM wrapper with a chart on top
The user

An AI infrastructure engineer with ten minutes, a p95 SLO, and a hardware budget due Friday. They do not want a simulator tour. They want to know which option to defend, where it breaks, and how to prove it to the person who signs the purchase order.

The lifecycle

Nine stages, one defensible decision.

The engineer loops between reading, iterating, and stress-testing until the answer survives scrutiny. The tool never decides; it removes the guesswork.

STAGE 0110 MIN · NO CODE

Write the decision down before you touch the tool.

I don't need a simulator. I need to know whether to buy two more nodes or a CXL shelf — and what evidence would change my mind.

What the engineer does

  • Names the workload, the current failure mode, and the target: p95 decode latency, cost per million tokens, or capacity headroom.
  • Writes the two options being compared and the threshold that separates them.
  • States what result would falsify the hypothesis.

What the tool should show

  • A one-page decision brief, not a dashboard.
  • It becomes the scenario name and the opening line of the demo.

Under the hood

  • Nothing yet. This artifact is what keeps every later run honest.

STAGE 0220 MIN · CONFIG

Describe the system you already have.

Four H100 nodes, 512 GiB DRAM each, one CXL pool at 180 ns. I can write that down in ten minutes — and the validator catches the unit mistakes before anything runs.

What the engineer does

  • Adds compute and memory nodes with explicit capacities, latencies, and bandwidths.
  • Adds fabric links: latency, bandwidth, in-flight bytes, queue depth, loss.
  • Sets page size, duration, warmup, and a seed.

What the tool should show

  • A topology preview that matches what they typed.
  • Field-level schema errors before the run, not stack traces during it.
  • No hidden defaults. Units are visible: ns and bytes/ns.

Under the hood

  • SPECS/config.schema.json → Pydantic.
  • Immutable normalized scenario + scenario hash.

STAGE 0315 MIN · WORKLOAD

Pick the memory behavior, not the model benchmark.

The KV cache grows a couple of MiB per token and decode dominates. That shape — not a tokens-per-second leaderboard — is what decides whether remote memory helps.

What the engineer does

  • Chooses a profile: KV decode, prefill, sparse attention, MoE, mixed, or an imported trace.
  • Sets model geometry and the request mix: context lengths, concurrency, arrival rate.
  • Checks the generated access pattern before spending compute.

What the tool should show

  • Working-set growth, locality, and whether pages are read-mostly or dirty.
  • “Synthetic” versus “measured” labels, always visible.

Under the hood

  • Closed-form KV sizing from layers, KV heads, head dim, dtype.
  • Seeded arrival process; trace replay with byte/time normalization.

STAGE 0410 MIN · EXPERIMENT DESIGN

Decide what “better” means before you run.

Local-only is the floor. Swap-to-remote is the dumb baseline. Hot/cold is my candidate. If they don't share a seed, the comparison is theater.

What the engineer does

  • Pins a baseline and selects candidates.
  • Sets policy parameters: thresholds, tick interval, residency, migration caps.
  • Confirms that the only difference between runs is the policy.

What the tool should show

  • The comparison matrix and an explicit “same seed, same trace, same start state” guarantee.
  • A parameter diff, not just a dropdown.

Under the hood

  • Policy interface: on_access, on_pressure, on_tick.
  • Every policy observes the identical event stream and pressure signals.

STAGE 051–20 MIN · EXECUTE

Run the smallest experiment that can change your mind.

60 simulated seconds, 5 s warmup, seed 42. If this is slow, it's a model bug — not a hardware problem. A sweep can wait.

What the engineer does

  • Runs one scenario and watches virtual time advance.
  • Optionally fans out a sweep across fabric latencies or seeds on Modal sandboxes.
  • Cancels safely: partial runs are still valid evidence.

What the tool should show

  • Events processed, queue depth, and current simulated time — not a fake spinner.
  • A run ID they can cite later.

Under the hood

  • heapq event loop with deterministic tie-breaking.
  • Independent seeded RNG streams for workload, policy, and faults.

STAGE 06THE PAYOFF

Read the bottleneck, not the headline number.

p95 went from 214 to 268 ms. That is not “remote memory is slow.” That is queueing on one link, for 40% of the run. I need to see where it happened.

What the engineer does

  • Compares percentiles, hit ratios, remote traffic, and migration volume.
  • Isolates the tier, link, and time window responsible.
  • Reads the latency-over-time curve to find the cliff.

What the tool should show

  • One sentence verdict, then the evidence.
  • Every chart filterable by node, link, and time.
  • A visible difference from the baseline, always.

Under the hood

  • Streaming aggregation over the event log; percentiles computed from sampled windows.
  • Each metric keeps a link back to the events that produced it.

STAGE 07THE LOOP

Ask why, then make the tool prove it.

If prefetching doubles wasted pages, it isn't free. I want the counterfactual — same seed, same trace, measured delta.

What the engineer does

  • Asks a grounded question about the run.
  • Inspects the cited events before trusting the answer.
  • Accepts a schema-valid patch and reruns the same seed.

What the tool should show

  • An explanation that references specific events, not vibes.
  • A diff, not a replacement scenario.
  • “Measured delta” after the rerun — never a predicted one presented as measured.

Under the hood

  • Meta open-weight model via Baseten.
  • Tool calls read telemetry; output must validate against the scenario schema.
  • Proposals are explicit runs, not silent mutations.

STAGE 08RESILIENCE

Break it before production does.

A pool that is 20% faster until one link degrades is not a win. I need to know how it fails, and whether the policy thrashes while it does.

What the engineer does

  • Injects a node failure, link degradation, or packet loss.
  • Sets MTBF and repair time for probabilistic failure.
  • Compares steady-state and degraded-mode metrics.

What the tool should show

  • A fault timeline aligned with the latency curve.
  • Recovery time, throughput loss, and whether data was lost.
  • Degradation, not just a binary pass/fail.

Under the hood

  • Deterministic fault schedule and seeded failure process.
  • Interrupted transfers emit terminal events with status.

STAGE 09PROOF

Ship evidence, not a screenshot.

If a teammate can't reproduce this in one command, I didn't finish the experiment. The run bundle is the deliverable.

What the engineer does

  • Exports the scenario, manifest, metrics, and optional event log.
  • Records seed, version, and scenario hash.
  • Shares a run link or attaches the bundle to a design doc.

What the tool should show

  • A copyable reproduce command.
  • A diff against the pinned baseline.
  • Byte-identical results on rerun — or a loud warning.

Under the hood

  • Run manifest, scenario hash, JSONL/Parquet outputs.

01 / DETERMINISM
The comparison must be honest

One unseeded random call or an unstable sort and every policy comparison is invalid. This is tested, not assumed.

02 / CALIBRATION
The model must state its error

“CXL is around 180 ns” is a preset, not a result. Credibility comes from publishing where the simulation diverges from measured traces.

03 / GROUNDED AI
The model may propose; only the run may measure

The co-pilot reads telemetry and suggests a diff. It never reports a delta it did not obtain from a rerun.

Recruiting

Three hires. Four seats.

You plus three people. Every function lands on one of these seats — including the non-technical work, which is not optional.

Paste-ready intro for candidates

We're building RmemFab, a deterministic simulator that tells AI infra engineers whether remote memory — CXL or RDMA — actually helps their workload. You give it a scenario (nodes, tiers, links, workload, policy), it emits a seeded event stream, and the dashboard shows where the latency actually goes. Ten-day hackathon team, three layers: engine, dashboard, and a grounded AI co-pilot. We need people who care that the numbers survive a rerun.

Scope

What is in, what waits, what is cut.

The demo must work offline and fit in two minutes. Everything else is negotiation.

Working demo

First 48 hours
  • Scenario load + schema validation
  • Local DRAM vs remote pool, one fabric link type
  • LRU and hot/cold policies, same-seed compare
  • Synthetic KV decode workload
  • p50/p95/p99, hit ratio, fabric utilization
  • CLI run + one exported bundle
  • Minimal run detail view

Winning build

By day 10
  • Prefetching + frequency-aware eviction
  • MoE profile and trace import
  • Fault injection and degraded-mode view
  • Modal sweep fan-out
  • Grounded co-pilot with cited events
  • Occupancy heatmap + comparison diff
  • Shareable run link

Explicitly cut

Say no out loud
  • Rust/PyO3 hot path
  • WebGL rendering for huge traces
  • Multi-user auth and orgs
  • Cost model beyond a rough estimate
  • Real hardware calibration suite
  • Any feature that needs a live network during the demo
The 2-minute demo

One scenario, one argument, one proof.

Rehearse this until it fits. Every beat maps to a stage above.
